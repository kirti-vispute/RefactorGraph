## 3. Model / ML Audit

Verified by reading `ml/models/gat_baseline.py`, and by grepping every
CodeBERT invocation site across the codebase.

- **Pipeline matches the claimed design**: AST parse
  (`ml/preprocessing/ast_parser.py`) → heterogeneous graph
  (`ml/graph/graph_builder.py`, 14 relation types) → structural features
  + frozen CodeBERT embeddings concatenated per class/method/function
  node (`scripts/augment_graphs_with_codebert.py` /
  `backend/app/inference.py`) → 2-layer `HeteroConv`/`GATConv` stack
  (`ml/models/gat_baseline.py`) → per-task linear heads → Design B
  method-to-class pooling for God Class → GNNExplainer (offline, see
  below).
- **CodeBERT is genuinely frozen, not just `.eval()`-switched**:
  every single invocation site is wrapped in `@torch.no_grad()`
  (`scripts/augment_graphs_with_codebert.py:57`,
  `scripts/extract_codebert_embeddings.py:56`,
  `backend/app/inference.py:100,115`) — no gradient is ever computed
  through it, and the training optimizer (`torch.optim.Adam(model.parameters(), ...)`
  in `scripts/tune_hybrid_optuna.py`) only ever receives the `HeteroGAT`
  instance's own parameters, never CodeBERT's.
- **GAT/classifier components are trainable**: confirmed — 269,315
  trainable parameters in the deployed `HeteroGAT` instance (computed
  this audit cycle's prior turn by instantiating the actual saved
  config).
- **Design B matches the deployed checkpoint**: `backend/app/inference.py:81`
  constructs `HeteroGAT(..., class_method_pool=True)`, matching exactly
  how `scripts/promote_god_class_retrain_seed43.py` trained the
  currently-deployed weights. Loading a mismatched-architecture
  `state_dict` would hard-error at `load_state_dict()` — since the
  live smoke test succeeded, this is empirically confirmed, not just
  structurally plausible.
- **No PGExplainer claim exists anywhere** — grepped the full codebase:
  every `PGExplainer` mention (`scripts/explain.py`,
  `docs/explainability_report.md`) explicitly explains why it is **not**
  used (a parametric explainer requiring its own training loop, ruled
  out per this project's "no rushed second training pipeline" rule).
- **No false PyExamine-integration claim exists** — grepped the full
  codebase: all 3 mentions (`ml/preprocessing/ast_parser.py`,
  `ml/preprocessing/metrics.py`, `tests/test_label_rules.py`) reference
  PyExamine only as prior art whose known false-positive pattern this
  project's own metric code was fixed against — never claimed as an
  integrated component.
- **No unsupported model-component claims found** in any doc reviewed.

**One significant finding, carried forward prominently to section 8 and
12**: GNNExplainer is real and does run (verified extensively — see
section 8), but **only offline**, never as part of the live `/analyze`
request path.

## 8. Explainability Audit

**Most significant finding of this audit** — stated plainly:

- **GNNExplainer is genuinely implemented and does run** —
  extensively verified this project cycle (`scripts/explain_candidate.py`,
  3 real bugs found and fixed while getting it working correctly against
  the actual deployed architecture, documented in
  `docs/godclass_formula_revision.md` section 12). Its output
  (`docs/explainability_report_candidate.md`, `models/hybrid_class_pool_tuned_fixed_data/explanations_val.json`)
  is real: computed edge importances, structural feature importances,
  and CodeBERT-importance means, all traced back to real VAL source
  files and real graph structure — no fabrication found.
- **PGExplainer is confirmed not used anywhere** (section 3).
- **However: GNNExplainer is an offline analysis tool only.** Grepped
  `backend/app/*.py` for any GNNExplainer/explainer reference — **zero
  matches**. Grepped `frontend/src` for any explainer/node_mask/edge_mask
  reference — **zero matches**. The live `/analyze` endpoint's
  `explanation` field (`backend/app/inference.py::_explanation_for`) is
  a plain structural-metrics string (e.g. `"loc=45, statements=12,
  self_access=2, external_access=5"`), computed directly from
  `ml/preprocessing/metrics.py` — **not** a GNNExplainer output, and the
  schema field is a plain `str` (`backend/app/schemas.py:49`), not an
  importance/attribution object.
- **Consequence**: "important nodes/edges are not fabricated" — true,
  but there is nothing live to fabricate, because no GNNExplainer output
  reaches a live request at all. "Frontend representation matches
  backend output" — vacuously true (frontend shows exactly the
  structural-metrics string the backend sends, nothing more), but this
  is a **different, much simpler claim** than "the frontend visualizes
  GNNExplainer's node/edge importance," which does not happen anywhere
  in the live system.

**This is not a bug** — everything the live system does, it does
honestly and correctly. It is a **claim-vs-implementation gap**: if any
poster/demo narrative implies GNNExplainer runs live, per-submission,
and its output is what the user sees highlighted in the interactive
graph, that would misstate what the deployed system actually does. See
section 12.
